# 车辆速度反馈与 P4 核查

2026-09-16 更新：已按最新“X 后、Y 下、Z 左”的机体系假设完成适配，并测试历史记录和新采集的 35 秒在线行驶反馈。**转换实现通过测试，实际反馈没有通过坐标与积分核验，不能直接用于位姿预测。** 实时配置继续为 **`enabled: false`、`fuse_velocity: false`**。实车标准 `sensor_msgs/Imu` 接口保留，见 [可选 IMU](optional_imu.md)。

此前先后收到过车体 FLU、世界系、Actor 机体系的说明，目前六个原始速度字段的表达坐标仍未核准，`wire_frame_confirmed: false`。世界模式和机体模式均已实现；世界模式只读取同报文姿态作速度换轴，不把仿真位置或姿态作为定位观测。`world_frame_alignment_confirmed: false`。

世界坐标假设下的旧记录仍未闭合：今日行驶段线速度留出窗口残差中位数约 0.103 m/s，而参考速度中位数约 0.079 m/s；从这一段选出的轴变换在长记录上也不一致。此处比较使用接收时间，不是远端采样时间，不能据此随意修改比例后启用积分。

## Actor 机体系候选实测

原始轴 X 后、Y 下、Z 左构成左手系。按该约定，普通线速度向量转 ROS 为 `(-vx, vz, -vy)`；如果角速度遵循对应的左手系轴向量约定，则转为 `(wx, -wz, wy)`，再按已约定的度/秒乘 `pi/180`。不能对两组原始字段使用相同的符号转换。

现有 C++ 接收器已经翻转了线速度 Y 和角速度 X/Z。因此，新编码 **`legacy_driver_from_actor_body_wire`** 专门用于已解码的 `/car/odom`，只执行以下同一个右手旋转，不能再撤销接收器的符号转换：

```text
ROS = C × decoded，C = [[-1,0,0], [0,0,1], [0,1,0]]
```

此编码只能配合 `velocity_frame: body`。已有 `base_from_feedback_rotation` 在编码转换之后执行，通常为单位矩阵；不要再次填入 C。机体模式不读取仿真位置或姿态，实车标准 IMU 路径不受该编码影响。

验证分为两部分：

- **实现验证通过**：16 项门控/坐标单测、1 项配置测试、3 种隔离 ROS/EKF 圆弧测试；包括前进、左右转、角速度符号、协方差换轴、数据过期和断流。6 个 ROS 包编译通过，安装代码与源码一致。
- **实际数据核验失败**：同一套固定换轴、m/s 与度/秒单位，测试 3 段旧记录和 35 秒新在线记录，没有针对轨迹拟合轴向、比例或时差。位姿仅用于评分，以及每段自由积分的初始对齐，没有喂入定位器。

| 记录 | 机体系速度方向误差中位数 | 10 秒自由积分终点误差中位数 |
|---|---:|---:|
| 当日早些时候人工行驶 | 19.1° | 0.103 m（含原地转向段） |
| 历史直行尾段，约 378 秒 | 76.0° | 1.29 m |
| 历史长轨迹，约 2117 秒 | 100.5° | 2.04 m |
| 本轮新在线反馈，35 秒、699 条 | 160.8° | 3.49 m |

这些是反馈坐标与接收时钟下的纯速度积分诊断，不是 LiDAR/视觉建图的 ATE。新记录共有 3 个不重叠的 10 秒积分窗口；其中一段参考路程 1.67 m，终点误差 4.21 m。未使用任意尺度拟合或事后轨迹对齐。

### 发现的具体规律

历史长轨迹中，车头约 36.7° 时，按 Actor 换轴后的速度方向约 -73.2°；车头约 89.5° 时约 -176.3°。新旧记录都表现出接近 **负两倍车头角度** 的方向变化，和固定机体系速度不符。它提示发送端可能有旋转方向、左右手系或重复变换问题；尚未取得发送端对应计算代码，不能据此确定具体错误位置。

只为诊断而补偿这项航向关系后，新在线记录的方向误差中位数降至 1.46°，但线速度残差仍为 0.107 m/s（参考速度中位数 0.127 m/s）。各记录的速度比例也不一致。因此，**该经验补偿没有加入生产代码**，需要继续核对发送端速度计算、单位以及仿真采样时间与接收时间的关系。禁止通过每条轨迹单独缩放来宣称标定成功。

真实接收测试仅从域 10 订阅，将未标定的候选速度发布在隔离域 63，没有发布车辆控制，也未接入域 57 定位。35 秒测试已结束；候选接收器内存峰值约 65 MiB。证据位于远程 `results/velocity_input_20260916/actor_body_trial/`，包括 `report.json`、`heading_diagnostic.json` 和 `live_receiver/`；原始数据不进入 Git。

## P4 实际读取的内容

- 源码：`/home/yanfa/P4/ros2_ws/src/lunar_obj_tcp_sim/lunar_obj_tcp_sim/` 下的 `protocol.py`、`coordinates.py`、`bridge_node.py`。
- P4 TCP 配置端口为 6668。其协议解析 108 字节封包：16 字节外头、4 字节 VehicleID、88 字节车辆反馈。反馈包含四轮速度、四轮转角、位置、四元数、三轴线速度、三轴角速度；没有加速度或远端采样时间戳。现有旧接收器还支持旧格式，不能直接替换解析器。
- P4 确认的 Actor 轴为 X 后、Y 下、Z 左；转成 ROS 车体向量是 `(-x, z, -y)`。世界坐标单独翻转 Y。这个定义适用于模型姿态，不能直接证明原始速度字段也在同一坐标系。
- P4 的 `PoseRates` 从转换后的位姿计算速度；线速度使用约 0.2 秒窗口，角速度由相邻旋转变化计算。接收间隔异常时导数无效。
- 当前联调版本 `debug/p3_joint/legacy_feedback_input.py` 复用域 10 的 `/car/telemetry`，向域 57 发布 `/P4/input/odometry`，没有另开 TCP 连接。该位姿来自仿真反馈，不是 P3 的定位结果；其差分速度不是 IMU 测量。

因此，这套 P4 桥接没有提供新的完整 IMU 接口。不能由此断言整个仿真没有 IMU。

## 坐标验证结果

只读提取 `20260824_235238` 的 42,349 条 `/car/odom`，覆盖约 2,117 秒和 151 度航向变化；没有回放控制消息。使用 P4 姿态转换后的位移、转角作为核验参考，不接入定位器。

现有旧驱动的 `base_link` 标签与建图车体系不一致。对原始速度简单套用 Actor 轴转换也未通过：航向约 32.8 度的一段，真实位移方向约 33.0 度，但转换后的“车体速度”方向约 -66.3 度；其他朝向也存在变化。不能只翻转 X 或靠一条直线拟合固定旋转。

1 秒窗口对照中，直接按 Actor 轴转换的线速度误差中位数约 0.197 m/s。此数是与位姿差分的速度残差，不是定位 ATE；窗口重叠、接收时间抖动和旧数据版本均限制其解释。新采集的行驶段也未通过简单固定轴转换。

角速度按用户约定使用度/秒，乘 `pi/180` 转为 rad/s；P4 旧转向记录也提示尺度尚未完全闭合。不能把单位约定当成实测标定完成。

本机证据保存在 `results/velocity_input_20260916/`，包括 `p4_coordinate_audit.json`、原始反馈提取及被动行驶记录；原始数据不进入 Git。

## 本模块的接入方式

启动命令不变：

```bash
./start_simulation_sources.sh  # 采集、控制与人工 GUI
./start_live.sh                # 建图与 RViz；仿真反馈当前关闭
```

6665 传图像、LiDAR、ToF；6668 传车辆控制和反馈。新节点订阅现有 ROS 接口，不争抢 TCP，不读取图像，也不发送车辆指令。

| 域／话题 | 用途 |
|---|---|
| 10：`/car/odom` | 读取速度、时间戳；世界速度模式额外读取同报文姿态作轴变换，不读取位置 |
| 57：`/fusion/telemetry_twist` | 单位转换与门控后的 `TwistWithCovarianceStamped` |
| 57：`/fusion/telemetry_status` | 接收、丢弃、新鲜度和是否参与积分的 JSON 状态 |

未标定时输出帧名为 `vehicle_feedback_unverified`。静止检测只使用速度模长：新鲜的运动反馈否决静止；零反馈仍须图像、点云等证据确认；超时不保留旧反馈为有效观测。

接收器保留最新一条消息，检查有限值、单调时间、帧标签、年龄及速度上限，不刷新旧数据时间戳。输出上限 25 Hz，实际频率受上游突发发送及合并影响，不补造测量。

`enabled`、`fuse_velocity` 与 `calibration_confirmed` 都开启时，才向现有 EKF 接入六维速度；世界模式还要求 `world_frame_alignment_confirmed`。当前均不启用。P4 的仿真位置和差分速度没有接入定位。
