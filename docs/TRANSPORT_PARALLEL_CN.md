# 并行采集与实时入口（2026-09-17）

## 改了什么

```
UE 单条 TCP（字节有序传输）
  → 接收 + 解码（原有重叠）
  → 完整批次校验、锁定该批时间戳
  → 最多 1 个待发布批次 → 独立 ROS 发布线程
                           ↓
ROS 域 10 → 独立接收线程 → 有界缓存 → 转换、发布、可选录包 → ROS 域 57
```

上一批 ROS 发布时，下一批可以继续接收、解码。仍然只保持一个 UE 采集请求在途；没有改变发送端协议，也没有让同一 TCP 连接的后续字节越过前面的数据。

### 实时性和一致性

- 发布队列只保留最新的一个**完整批次**，另有一个正在发布的批次。拥堵时替换旧待发批次，不持续增加延迟。
- 批内图像和点云使用同一份不可变时间戳，避免线程切换后错误使用下一批时间戳。时间戳不改成处理完成时间。
- 默认单批保留载荷上限 64 MiB，整个 TCP 批次累计载荷上限为其两倍。TCP 声明长度、PNG 解码尺寸、解码后的总字节数均检查上限。
- 默认采集发布年龄上限 3 秒；排队年龄同时检查系统时间和单调时钟。系统时间回拨不会把排队的旧数据重新变新。
- 图像、LiDAR、IMU 在转接入口统一检查倒序、重复、过期和未来时间；LiDAR 默认年龄上限 3.5 秒，IMU 默认 0.5 秒。
- 转接接收线程不执行图像转换、DDS 发布或录包。缓存最多两个未匹配帧/相机、一对完整双目、一帧 LiDAR、256 个 IMU 样本；工作线程另持有当前处理组。IMU 保留时间顺序，溢出和输入空档都有计数。
- 双目先配对、两张都转换成功后再发布；某张解码失败，不把另一张独自当成完整视觉输入。
- 可选录包在双目发布后进行；录包报错会停止录包并记录错误，传感器转接继续。重启转接时另开 `live_input_bag_resume_*`，保留原 bag。
- TCP 中断、坏批次和发布异常均保留错误记录；坏批次不进入正常批次队列。正常结束可排空最新待发批次，停止时可取消待发队列。

**ROS 不提供多个话题写入的原子事务。** 如果已经进入 DDS 的一次写入中途卡住，恢复后可能出现一个迟到的单独消息。因此保留转接的年龄检查、双目配对和现有视觉/融合质量保护；不能仅凭“入发布队列前有效”判断数据仍可用。

这些是有界缓存和故障恢复措施，不是硬实时保证。队列上限也不是整个进程的内存上限：当前接收批次、解码工作区、DDS 缓存和消息序列化仍需要内存。

## 怎么用

仍使用原来的启动入口。私有采集编译：

```bash
cd ~/P3/lidar_visual_fusion
./scripts/build_capture_transport.sh
```

构建后原子替换本项目私有二进制；已经运行的采集进程继续使用旧版本，重新启动采集才生效。原 P3 capture 的源码和安装目录不修改。

直接启动 capture 时，可显式指定当前 UE 地址：

```bash
ROS_DOMAIN_ID=10 ROS_LOCALHOST_ONLY=0 \
  ./scripts/start_capture_source.sh --host <当前UE地址> --capture-freq 2
```

已有采集进程时不要重复运行上述命令。`2` 是请求频率上限，不保证网络和 UE 能提供 2 Hz。

可选参数（通常保持默认）：

| 环境变量 | 默认值 | 作用 |
|---|---:|---|
| `P3_CAPTURE_PARALLEL` | `true` | `false` 回到同步发布，便于对照 |
| `P3_CAPTURE_MAX_AGE_SEC` | `3.0` | 采集发布年龄上限 |
| `P3_CAPTURE_BATCH_MIB` | `64` | 单个待发布批次载荷上限 |
| `P3_CAPTURE_TIMEOUT_SEC` | `10.0` | 启动器的 TCP 读写/批次超时；超时重连，不无限等待 |
| `P3_CAPTURE_OPTIMIZED` | `auto` | `0` 使用原 P3 采集程序 |

转接可通过 profile 的 `live_transport` 配置 `lidar_max_age_sec`、`imu_max_age_sec`、`imu_queue_samples`。保持 IMU 接口并不代表已启用遥测融合。

## 怎么查问题

- `/sensor/batch_status` 保留原统计字段，并增加 `transport`：接收/准备耗时、解码耗时、排队时间、传感器发布时间、最慢传感器、消息年龄、替换/过期/异常计数。
- LiDAR 日志分别记录点云消息构造耗时 `build` 和 DDS 写入耗时 `dds_write`。
- `/sensor/meta` 发布完整且校验通过批次的原始 JSON；保留最新一条，供核对源时间和可选运动字段。它不是 `sensor_msgs/Imu`。
- 本轮运行的 `live_session_status.json` 增加待处理数量、转发年龄、最大输入空档、工作线程占用时间及 `degraded` 状态。
- 原始 meta 另保存为该轮的 `latest_sensor_meta.json`，不输入定位器。
- `input_gap` 表示传感器时间出现空档；`stale` 表示本机收到或准备转发时已过期；`replaced` 表示下游来不及处理旧待发数据。

### “前面堵住，后面还能发吗？”

如果堵在本机 ROS 发布，这套流水线仍能继续接收下一批。如果堵在 UE 发送、单条 TCP 链路或接收解码本身，后续采集仍受它影响。独立的高频运动反馈需要发送端提供独立连接/协议，不能仅靠接收端多线程实现。

## 已完成的验证

全部在 216 的 localhost ROS 域 89/90、模拟 TCP 服务上测试，没有连接 UE 或控制车辆。

- C++ 队列：消费者阻塞时连续提交 10000 批、最新完整批替换、字节上限、排空、取消、反复重置和唤醒。
- Python 入口：13 项测试，覆盖成对同步、过期 LiDAR、重复/乱序、时间回拨、内存边界、IMU 顺序与溢出、长空档后新帧及退出。
- 真 capture + 真转接程序：正常和串行兼容模式均通过。
- 在第二批左图 ROS 写入处故意停顿 **18 秒**：共请求 230 批，替换 164 个旧待发批次；迟到左图约 18.01 秒，在转接入口被拒绝。进入域 90 的双目各 64 帧、点云 64 帧，最大观测年龄约 **0.373 秒**。恢复后接到最新帧。
- 故障测试：512 MiB 非法包长、损坏 PNG、半批断连均未进入正常输出，重连后恢复，进程正常退出。
- 完整尺寸：2448×2048 BGR 双目 + 131072 点 LiDAR，共 12 批均完整收到、时间戳对齐；采集 RSS 采样峰值约 **180.4 MiB**。

完整尺寸测试使用易压缩的合成图像和 localhost，验证内存/ROS 路径及同步，**不是 UE 有线网络的性能测量**。尚需 UE 恢复后的持续在线观测确认真实延迟和图像负载。

证据：`results/capture_parallel_20260917/`。`blocked_1789647582563716141` 是早期故障注入误命中初始化日志的失败试验，不能用于并行效果结论；有效阻塞试验为 `blocked_1789647726997834868`。

## IMU 当前结论

216 近期五个已结束 bag 的 `/imu/data` 均为 0；已检查的 6668 协议缺少加速度和发送端采样时间。速度/角速度的候选换轴也未通过记录一致性校验，暂不接入位姿预测。

保留实车标准 `sensor_msgs/Imu`、安装外参、时间和质量检查。后续若确认角速度/线速度有效，可走独立速度辅助入口，不用填零加速度来模拟完整 IMU。详细报告见 `results/imu_recent_audit_20260917/IMU_AUDIT_216_20260917.md`。
